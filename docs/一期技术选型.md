# 一期技术选型（独立知识项目版）

更新：2026-09-07。架构已按第一期拆分执行，原文归档在 history。

## 是否从零开发

不从零开发模型网关。LiteLLM 负责供应商适配、模型别名和虚拟 Key；Opsark 自研平台业务界面、知识上传/审核/版本/检索业务。知识服务不是额外部署一套平台用户系统。

| 项目/层 | 选型 | 当前实现 |
| --- | --- | --- |
| admin Web | Vue 3 + Vite | 可构建的管理页面，当前采用轻量原生组件/CSS，未引入 Element Plus |
| admin API | FastAPI + SQLAlchemy + Argon2 | 身份、会话、CSRF、远程知识管理适配 |
| knowledge API | FastAPI + SQLAlchemy | 上传契约、Key、审核版本、检索与审计 |
| knowledge Worker | 独立 Python 进程 + 持久化任务表 | 草稿、索引、租约和重试 |
| 数据库 | 两个独立 PostgreSQL；知识侧加 pgvector | SQLite 分库用于本地开发/自动测试，生产适配待环境验证 |
| 检索 | jieba + 关键词/可选 Embedding + 融合排名 | 首版应用层精确扫描；PG 原生全文索引及大规模近似索引后续优化 |
| 模型网关 | 独立 LiteLLM | 提供可选 Compose profile 和参数模板，未连接真实供应商 |
| 部署 | 各项目独立 Dockerfile/Compose | 模板已生成，当前机器尚未执行 Docker 验收 |

## 服务间通信

平台仅通过固定 KNOWLEDGE_URL 调用知识内部白名单路径。浏览器不能指定任意上游 URL；请求使用服务 Token，控制面 Key 不下发客户端。超时/故障返回明确的 503，平台登录保持可用。

两个项目各有 pyproject.toml、constraints.txt、迁移和测试；不共享 Python 包或数据表。开发机可以让端口 8001/8002 同时运行，生产可以分别上服务器。

## 模型部署与商业许可

第一期不训练/部署模型权重，不需要 GPU。模型和 Embedding 使用外部 API；知识无 Embedding 时也能以关键词模式运行。

LiteLLM 企业目录外采用 MIT，企业目录另有许可；FastAPI 使用 MIT，pgvector 使用 PostgreSQL 许可。可用于商业产品，但要保留相应许可声明，逐版本核对依赖；上游模型 API 是否允许提供收费接口需单独确认供应商条款。[LiteLLM LICENSE](https://github.com/BerriAI/litellm/blob/main/LICENSE)、[FastAPI LICENSE](https://github.com/fastapi/fastapi/blob/master/LICENSE)、[pgvector LICENSE](https://github.com/pgvector/pgvector/blob/master/LICENSE)

社区功能与企业功能不混用。LiteLLM 按模型分别预算、企业身份功能不计入本期免费能力保证。无 Redis 时固定单副本单 worker；增加进程前再设计共享状态。[LiteLLM Redis 要求](https://docs.litellm.ai/docs/proxy/redis_requirements)

Dify、RAGFlow 和 New API 未加入当前运行依赖；原有对比见历史技术选型。未来选用时重新核查许可和功能，不能继承未经验证的商用结论。

## 版本与生产门槛

已记录本地 Python 依赖约束和 npm lock。Compose 中的基础镜像 tag 是开发模板，生产部署前需要固定发行版本/digest 并核对 SBOM。初始数据库迁移适用于新项目；如果使用过旧混合数据库，应先备份并单独设计数据迁移，不直接覆盖。

正式上线还要验证 TLS、服务 Token 轮换、日志/备份保留、真实供应商 thinking/JSON/输出上限兼容。应用层检索和默认限流适用于单进程开发版，当前未声称达到 5 万切片的性能目标。
