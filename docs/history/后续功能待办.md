## 2. 第一期只保留这些扩展点

- 稳定的文档/版本/来源 ID，后续可关联记忆和同步状态。
- `installation_id` 与知识库授权；后续明确迁移到用户/空间的映射，不提前开放跨租户共享。
- 模型别名、实际请求 ID、usage 来源标记；未来账本不能直接把运营统计当正式流水。
- `BlobStore` 与 `EmbeddingProvider` 接口，后续替换存储和模型不改变上传协议。
- 版本化 `/api/v1` 与 `schema_version`，不通过随意增加匿名字段演进接口。

不提前实现钱包空表、记忆自动提取、支付回调占位、团队角色页面或同步守护进程。

## 3. 关于“用户记忆”的保留结论

用户原始诉求中的记忆功能仍在路线图中，但第一期的知识记录不等于用户记忆：

- 知识记录是人工选择上传并审核发布的资料。
- 任务内检查点仍留在 core，继续处理当前任务进度。
- 长期记忆需要额外的身份、同意、证据、有效期、冲突和删除设计。

因此第一期不会将后台收集的任务记录自动写成用户画像，也不会因为知识库保存了某次环境信息，就在以后执行时默认服务器状态未变。

## 4. 后续进入设计的方式

每项功能单独建立设计文档，记录实际用户场景、范围、数据流、迁移、成本、验收和依赖。由产品优先级决定顺序，不默认表格编号就是开发顺序。

若第一期之后优先商业化，先设计 FUT-01/FUT-02；若优先提升运维效果，先评估 FUT-06/FUT-11；长期记忆 FUT-04/FUT-05 保持独立评审，不作为知识库索引的附带功能自动上线。
