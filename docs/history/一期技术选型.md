# Opsark_admin 第一期技术选型

决策日期与资料核对日期：2026-09-06。结论基于当前需求、core 源码和官方文档；尚未运行部署 PoC。开发开始时必须固定实际发行版本、镜像摘要、依赖锁文件和对应许可证。

## 1. 是否需要从 0 开发

**不需要从 0 开发模型网关和底层检索组件；需要自研 Opsark 特有的知识业务流程。**

| 工作 | 决策 | 原因 |
| --- | --- | --- |
| 供应商协议转换、模型别名、虚拟 Key、基础用量 | 复用 LiteLLM Proxy | 无需重复实现已有网关能力 |
| 模型管理界面 | 优先复用 LiteLLM 原生管理控制面 | 第一期不复制一套完整模型运营后台 |
| HTTP 契约、校验、数据库迁移 | FastAPI/Pydantic、SQLAlchemy/Alembic | 使用成熟组件，业务接口仍由我们定义 |
| 向量、关键词数据基础 | PostgreSQL + pgvector + 中文分词 | 数据与权限同库，减少一期运维组件 |
| 上传、脱敏规则、审核、版本、引用 | 自研 | 这些规则直接依赖 Opsark 运维任务与执行证据 |
| 通用 RAG/Agent 编排 | 不引入强依赖 | 当前固定处理链无需可视化工作流平台 |
| Embedding 模型 | 调用已有服务，不训练模型 | 以中文运维样本筛选一款，版本固定 |

因此“新建 admin 项目”不等于“从头造所有底层能力”。一期代码集中在小型管理业务和 core 接口契约上。

## 2. 主选技术栈

| 层 | 选择 | 一期用法与边界 |
| --- | --- | --- |
| 管理前端 | Vue 3 + TypeScript + Vite，Element Plus | 与 core 的 Vue 技术经验一致，独立项目；不直接复制 Tauri 页面 |
| 业务 API | Python + FastAPI + Pydantic | JSON 校验、上传、查询、管理 API、OpenAPI |
| ORM/迁移 | SQLAlchemy + Alembic | 业务数据库迁移；不管理 LiteLLM 表结构 |
| 数据库 | PostgreSQL + pgvector | 文档、来源、版本、队列和向量；从精确检索开始 |
| 中文关键词 | jieba 搜索分词 + 运维词典 + PG `simple` 全文配置 | 自然语言分词；路径/错误码另存精确词项 |
| 模型网关 | LiteLLM Proxy 社区功能 | 非流式兼容调用、别名、virtual key、基本限额/用量 |
| 后台任务 | 独立 Python Worker + PostgreSQL 任务表 | 单 Worker 起步，持久化队列、租约和有限重试 |
| 文件 | 本机挂载的持久卷，抽象 `BlobStore` 接口 | 一期小型 MD/TXT 文件；不先部署独立对象存储集群 |
| 入口 | Caddy | HTTPS、静态资源、路径白名单反代 |
| 部署 | Docker Compose，生产 Linux | 单机初版，开发可在 Windows 的容器环境运行 |
| 验证 | pytest、前端组件测试、接口契约测试、轻量压测 | 重点验证隔离、幂等、发布一致性和 core 协议 |

FastAPI 提供基于 OpenAPI/JSON Schema 的接口描述和校验，适合两个独立项目按契约开发。[FastAPI Features](https://fastapi.tiangolo.com/features/)

Vue 组件库与部署入口选择属于本项目的工程判断。对应官方资料：[Element Plus](https://element-plus.org/en-US/guide/design.html)、[Caddy](https://caddyserver.com/docs/)。

不强制沿用 core 的 Rust 实现服务端：现有 Rust 主要服务于桌面 SSH/Tauri，知识处理使用 Python 可以直接接入解析、分词和检索组件。若团队实际以 Rust 为主，可在 M0 重新评估，但保持对外契约不变；这不是一期同时实现两套后端。

## 3. 模型网关对比

| 候选 | 优势 | 一期代价/限制 | 决策 |
| --- | --- | --- | --- |
| LiteLLM Proxy | 模型协议适配、别名、虚拟 Key、原生 UI，可独立作为模型服务 | 需固定版本验证社区功能及供应商参数适配 | 主选 |
| New API | 自带渠道、用户令牌、额度和运营界面 | 当前不做用户付费，较多运营能力闲置；许可证和 NOTICE 需随版本核对 | 备选，未来若走现成模型运营平台路线再评估 |
| 自研模型代理 | 完全自主接口 | 需要承担多供应商协议、错误、Key、重试、限流和维护 | 一期不选 |

LiteLLM 官方 Quickstart 提供 PostgreSQL、原生 UI 添加模型和生成虚拟 Key 的路径；虚拟 Key 文档说明模型允许列表等能力。[Quickstart](https://docs.litellm.ai/docs/proxy/docker_quick_start)、[Admin UI](https://docs.litellm.ai/docs/proxy/ui)、[Virtual Keys](https://docs.litellm.ai/docs/proxy/virtual_keys)

New API 当前仓库提供渠道/协议转换和运营功能，部署细节以其当前 Compose 为准，不套用旧归档文档。[New API README](https://github.com/QuantumNous/new-api/blob/main/README.md)、[Compose](https://github.com/QuantumNous/new-api/blob/main/docker-compose.yml)

### LiteLLM 的社区版使用边界

- 一期使用基本模型配置、Key 创建/查询/撤销、允许模型、整体预算和基础限流；M0 必须在没有 Enterprise license 的条件下实测。
- 官方将 `model_max_budget`（同一 Key 按模型分别设置预算）标为 Enterprise；不列入一期承诺。
- SSO/SCIM、复杂组织权限、企业审计等不作为一期免费依赖。Opsark 自己的知识审核审计仍需自研。
- 使用分发给 core 的非管理员 Key 验证限流；管理员凭据的行为可能不同。
- 若某项原生 UI 不可用但稳定管理 API 可用，先使用受保护 API，不扩大为完整自研模型控制台。

来源：[Budgets / Rate Limits](https://docs.litellm.ai/docs/proxy/users)、[Key 管理实现](https://github.com/BerriAI/litellm/blob/main/litellm/proxy/management_endpoints/key_management_endpoints.py)。

### Redis 和部署模式

一期若不部署 Redis，必须固定 **LiteLLM 单副本、单 worker**；不能仅写“单容器”就默认满足。增加 worker/副本前加入共享 Redis，并验收跨进程限流、Key 撤销与缓存一致性。官方说明多 worker 存在共享状态需求。[Redis Requirements](https://docs.litellm.ai/docs/proxy/redis_requirements)

知识业务 API 同样按单副本起步，限额以持久化状态或经过验证的统一入口实现；后续多副本不能沿用各自的内存计数。

模型用量/预算仅作运营保护，不是原子预付账本，也不承诺供应商花费在并发下严格零超额；正式付费系统另行设计。

## 4. 知识底座对比

| 候选 | 官方能力 | 适用性判断 |
| --- | --- | --- |
| FastAPI + PostgreSQL/pgvector 薄业务层 | API 校验、向量/全文混合检索基础 | 主选，贴合结构化记录和纯文本审核流程 |
| RAGFlow | 文档上传、解析、切片、检索 API，以及复杂文档处理能力 | 复杂 PDF/扫描件增加后再评估；纯文本一期收益不足以抵消额外部署与适配 |
| Dify | 知识库、应用、插件和工作流综合平台 | 当前不需要应用编排，且仍要自建 Opsark 的审核/版本业务层 |

pgvector 官方提供混合全文检索与 RRF 排序示例；不需要为这条固定流程强制引入 LangChain 或 LlamaIndex。后者是否加入取决于后续需求，而非 RAG 的必选前提。[pgvector](https://github.com/pgvector/pgvector)

RAGFlow 的官方 Quickstart 当前列出最低 4 核、16GB 内存、50GB 磁盘，这只是该项目的文档要求；它也提供上传和检索 HTTP API。[RAGFlow Quickstart](https://github.com/infiniflow/ragflow/blob/main/docs/quickstart.mdx)、[HTTP API](https://ragflow.io/docs/http_api_reference)

Dify 官方 Compose 部署包含多项核心和依赖服务。对本期仅有 JSON/MD/TXT 的链路，引入整个平台不是必要条件。[Dify Docker Compose](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)

### 检索实现约束

- jieba 搜索模式配合版本化运维词典；文档和查询使用同一分词配置。[jieba](https://github.com/fxsjy/jieba)
- `exact_terms` 保存大小写按类型规范化的完整路径/错误码/服务名；Linux 路径不能统一转小写。
- 自然语言、精确项和向量各自召回，业务层用固定的融合策略排序。首期不引入另一个付费重排 API。
- `pg_trgm` 可作后续模糊匹配补充，它忽略非词字符，不能代替命令和路径精确匹配。[PostgreSQL pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)
- 初期精确向量排序足够时不提前加近似索引；加 HNSW 后，单独测试权限和版本过滤导致的召回不足。[pgvector Filtering](https://github.com/pgvector/pgvector#filtering)

## 5. 队列和文件存储为什么先做轻量方案

上传记录和入队同事务，Worker 以 `FOR UPDATE SKIP LOCKED` 认领任务，再使用租约处理长任务，失联后可重新认领。PostgreSQL 官方明确这种跳过锁定行的方式适合多个消费者访问队列类表，但不用于一般一致性查询。[PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)

这不意味着只调用 FastAPI 进程内后台任务就足够：API 重启后任务不能丢失，索引结果还必须幂等。

文件只支持小型 MD/TXT，采用持久卷和生成式对象 ID；客户端文件名只作展示，不参与磁盘路径拼接。未来需要多机/大文件时，通过 `BlobStore` 接口接对象存储，不改文档来源主键。

## 7. 资源与版本锁定建议

- 初期试运行可从单机 4 vCPU / 8GB RAM / 50～100GB SSD 开始评测，模型和 Embedding 使用外部服务、不在此机器部署推理模型。该规格是估算起点，不是容量保证。
- 基准数据集暂定不超过 1 万文档/5 万切片、检索并发 5；以 M4 压测调整机器和索引，不将试运行规模写成产品硬上限。
- 记录每个镜像的发行 tag 和 digest，不使用浮动 `latest` 上线；Python/Node/PostgreSQL 主版本在 M0 按兼容矩阵锁定，不在当前未验证环境中虚构补丁版本。
- 生产备份覆盖数据库、附件以及解密所需的密钥恢复流程；密钥恢复材料单独加密保管，不能与公开部署文件混存。
- LiteLLM UI 存储上游 Key 使用的 `LITELLM_SALT_KEY` 需要稳定保存并纳入恢复演练；不能恢复数据库后临时换一个 salt。[LiteLLM Quickstart](https://docs.litellm.ai/docs/proxy/docker_quick_start)

## 8. M0 决策门槛

启动开发后先用 2～3 人日做无企业 license 的 PoC：

1. 通过原生管理入口创建模型、非管理员虚拟 Key、允许模型列表并撤销。
2. 使用 core 实际参数验证 `/models`、Chat Completions、JSON 输出、thinking 字段处理、输出上限和错误格式。
3. 检查 Key 限流/预算和供应商凭据恢复行为，确认单 worker 设置有效。
4. 用 30～50 条合成/脱敏运维资料确认中文、路径、错误码的检索方案，并选择 Embedding 配置。
5. 保存组件版本、功能验证结果、许可证清单和失败项。

若某些模型不兼容，先缩小一期模型列表，不把协议问题带入正式开发；若主选网关基础能力不能在社区版满足需求，形成新 ADR 后切换备选。未通过 PoC 前不承诺商业收费能力或全供应商兼容。
