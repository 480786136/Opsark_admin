## 目录与项目边界

实际目录为 `E:\vscode\Opsark_admin` 和 `E:\vscode\Opsark_core`。用户输入中的 `Opsark\_admin`、`Opsark\_core` 按现有目录名理解为下划线；没有新建 `E:\vscode\Opsark\_admin` 这样的嵌套目录。

- **Opsark_admin**：独立开发、部署的 Web 管理端与服务端。第一期只做知识库和模型接入。
- **Opsark_core**：现有 Tauri + Vue + Rust 桌面运维客户端。通过 HTTP 接口消费 admin 能力，保持独立发布。
- 两个项目不共享数据库、不相互导入源码、不要求放入同一个 Git 仓库。
- 本次只在 admin 目录生成文档，没有修改 core。

## 一期结论

采用 **Vue 3 管理界面 + FastAPI 业务服务 + PostgreSQL/pgvector + 独立 LiteLLM Proxy + Docker Compose**。

不从零编写模型网关，也不开发通用 Agent 平台。复用模型协议适配、虚拟 Key 和模型路由能力；自研 Opsark 特有的记录上传、审核整理、发布、引用检索与小型管理界面。

交付两条闭环：

1. `core 选择并脱敏记录 → admin 接收 → 管理员整理审核 → 发布为知识 → core 检索带来源的片段`。
2. `管理员配置供应商 → 发布模型别名 → 签发模型 Key → core 配置 base_url、API Key、model → 完成模型调用`。

一期没有注册会员、充值扣费、套餐、用户长期记忆或团队协作。管理员登录、机器 Key、基本隔离、调用用量及审计属于一期必要基础，不等于完整用户或计费系统。

## 配置交付示例

以下域名和 Key 均为文档占位值，不可直接连接。

| 用途 | 地址或配置 | 凭据 |
| --- | --- | --- |
| 模型 | `https://api.opsark.example/v1`，模型名例如 `opsark-general` | 模型虚拟 Key，在 LiteLLM 控制面生成 |
| 知识接口 | `https://api.opsark.example/api/v1` | Opsark 知识 Key，由业务服务生成 |
| 管理页面 | `https://admin.opsark.example` | 管理员账号/会话 |

模型 Key 和知识 Key 分开，互不通用。它们可以分别轮换和禁用。第一期不为统一成一把 Key 而额外自研模型转发层。
