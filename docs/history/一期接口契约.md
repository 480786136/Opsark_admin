# Opsark_admin 第一期接口契约

版本：设计草案 v1，2026-09-06。本文件描述目标接口，不表示服务已上线。实现时由 FastAPI/Pydantic 生成 OpenAPI，并将契约快照提交仓库供 core 独立联调。

## 1. 地址和认证

| 配置 | 示例 | 说明 |
| --- | --- | --- |
| 模型 base URL | `https://api.opsark.example/v1` | core 的 endpoint 填此值，不填完整 completions 路径 |
| 模型 Key | `MODEL_KEY_REPLACE_ME` | LiteLLM 签发的非管理员虚拟 Key |
| 模型名 | `opsark-general` | 已发布且该 Key 可用的别名 |
| 知识 base URL | `https://api.opsark.example/api/v1` | Opsark 业务 API |
| 知识 Key | `KNOWLEDGE_KEY_REPLACE_ME` | 业务服务签发，绑定安装标识和知识库权限 |

两类 API 都使用 `Authorization: Bearer <key>`，但凭据不通用。供应商原始 Key、LiteLLM master key 不能提供给 core。知识接口禁止用 query string 传 Key。

知识 Key scopes：`records:write`、`records:read`、`knowledge:read`。除 scope 外，还需要目标知识库授权；知道资源 ID 不能绕过权限。普通 Key 没有审核、发布、管理渠道或签发 Key 的权限。

JSON 采用 UTF-8；时间使用含时区的 RFC 3339 字符串，响应统一为 UTC。未知请求字段返回 `422`，防止 core 意外将额外日志内容上传。

服务端生成 `request_id` 并通过 `X-Request-ID` 返回；客户端 trace ID 仅作辅助关联，限制长度并清理控制字符，不能作为身份或幂等依据。

## 2. API 清单

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /v1/models` | 模型 Key | 获取本 Key 可调用的模型 |
| `POST /v1/chat/completions` | 模型 Key | 兼容 core 的模型调用 |
| `POST /api/v1/records` | `records:write` + 目标库上传授权 | 接收一条结构化记录 |
| `GET /api/v1/records/{record_id}` | `records:read` + 自己的安装归属 | 查询接收、整理和审核状态 |
| `GET /api/v1/knowledge/bases` | `knowledge:read` | 列出授权可检索的知识库 |
| `POST /api/v1/knowledge/search` | `knowledge:read` + 库授权 | 返回带引用的知识片段 |
| `GET /api/v1/knowledge/documents/{document_id}/versions/{version}` | `knowledge:read` + 文档所属库授权 | 获取可访问的发布版本和引用内容 |
| `GET /health/live` | 无，返回最小信息 | 进程存活 |
| `GET /health/ready` | 内部监控或受保护入口 | 业务数据库、迁移等就绪状态 |

管理 API 使用独立管理员会话，前缀 `/api/admin/v1`；不能拿机器知识 Key 调用。

## 3. 模型接口

请求示例，使用合成提示词，不包含真实运维资料：

```http
POST /v1/chat/completions
Authorization: Bearer MODEL_KEY_REPLACE_ME
Content-Type: application/json
```

```json
{
  "model": "opsark-general",
  "messages": [
    {"role": "system", "content": "Return one JSON object."},
    {"role": "user", "content": "Return a field named ok with value true."}
  ],
  "response_format": {"type": "json_object"},
  "stream": false
}
```

兼容响应示例：

```json
{
  "id": "chatcmpl-example",
  "object": "chat.completion",
  "model": "opsark-general",
  "choices": [
    {
      "index": 0,
      "message": {"role": "assistant", "content": "{\"ok\":true}"},
      "finish_reason": "stop"
    }
  ],
  "usage": {"prompt_tokens": 28, "completion_tokens": 6, "total_tokens": 34}
}
```

一期兼容要求：

1. 返回 JSON，`choices[0].message.content` 为字符串；不能只返回自定义 `answer` 或 `tool_calls`。
2. 支持 `/models` 和非流式 `/chat/completions`；SSE 可作为网关能力存在，但不纳入 core 首期验收。
3. core 现有请求可能包含 `thinking: {"type":"disabled"}`。逐模型映射或有针对性地去除不受支持的可选 thinking 字段；不得全局丢弃 `response_format` 等关键约束。
4. 不支持 core 所需结构化输出的模型，不应进入首期可选列表；不能用提示词“尽量输出 JSON”冒充已完成兼容验收。
5. 使用 core 实际的需求理解、规划、复核、调整请求样本回归，不只测试一句普通聊天。
6. `GET /models` 只暴露授权别名，不返回上游 Key、供应商管理地址或未授权模型。
7. 由 LiteLLM 透传/规范化的错误采用其兼容响应；core 不能依赖供应商内部错误文本。
8. 即使 core 未传 `max_tokens`，也必须应用该别名经过验收的服务端输出上限；真实 `finish_reason=length` 不得改成 `stop`。计划解析会拒绝非正常结束的内容。

现有 core 最多进行 3 次传输尝试；一期网关 `num_retries` 设为 0，并禁用自动跨模型 fallback。连接断开后上游可能已消耗 Token，不能承诺请求在供应商侧恰好执行一次。模型请求没有知识上传接口那样的业务幂等保证。

模型请求容量和超时在选定模型实测后配置，反向代理不应使用短于业务请求的超时。上线前对照 core 各类请求的真实 `timeout_seconds` 建表验收，避免代理提前断流。

## 4. 上传知识来源记录

### 4.1 请求

```http
POST /api/v1/records
Authorization: Bearer KNOWLEDGE_KEY_REPLACE_ME
Idempotency-Key: upload-demo-record-001-r1
Content-Type: application/json
```

```json
{
  "schema_version": "1.0",
  "source_record_id": "task-demo-001",
  "source_revision": 1,
  "knowledge_base_id": "kb-operations",
  "record_type": "task_result",
  "title": "Nginx 配置检查与重载案例",
  "occurred_at": "2026-09-06T02:00:00Z",
  "context": {
    "project_ref": "project-demo",
    "server_ref": "server-demo",
    "environment": "test",
    "software": [{"name": "nginx", "version": "example-version"}]
  },
  "problem": "修改配置后，需要验证配置并重载服务。",
  "steps": [
    {
      "step_id": "step-01",
      "description": "检查配置语法",
      "command": "nginx -t",
      "execution_status": "succeeded",
      "validation_status": "passed",
      "evidence": [
        {
          "evidence_id": "evidence-01",
          "kind": "command_result",
          "summary": "配置语法检查通过",
          "excerpt": "syntax is ok; test is successful"
        }
      ]
    }
  ],
  "outcome": {
    "status": "partial",
    "summary": "配置检查通过；此记录没有提供重载执行证据。"
  },
  "tags": ["nginx", "配置检查"],
  "redaction": {"client_applied": true, "ruleset_version": "core-upload-v1"}
}
```

示例故意将结果标为 `partial`：只有配置检查证据时，不能自动生成“重载成功”的知识结论。

### 4.2 字段约束

| 字段 | 约束 |
| --- | --- |
| `schema_version` | 一期仅接受 `1.0`，其他版本返回 `422` |
| `source_record_id` | 必填，1～128 字符；同安装标识内稳定 |
| `source_revision` | 正整数；修订上传用新 revision，不覆盖旧来源 |
| `knowledge_base_id` | 必填，必须在该知识 Key 上传授权内 |
| `record_type` | `task_result`、`incident_note`、`manual_note` |
| `title` | 1～200 字符 |
| `problem` | 1～8000 字符 |
| `context` | 可选，仅允许列明字段；project/server 使用非秘密标识 |
| `steps` | 0～30 步，`command` 可省略；command 最大 4000 字符 |
| `execution_status` | `succeeded`、`failed`、`blocked`、`not_run`、`unknown` |
| `validation_status` | `passed`、`failed`、`unknown`、`not_run` |
| `evidence` | 每步最多 5 项；每项 `summary` ≤1000、`excerpt` ≤2000 字符 |
| `outcome.status` | `succeeded`、`failed`、`partial`、`unknown` |
| `outcome.summary` | 必填，最多 4000 字符 |
| `tags` | 最多 20 个，每个最多 40 字符 |
| `redaction` | 客户端声明，仅作记录；服务端仍独立检查 |

总 HTTP 解压后正文不得超过 256 KiB，最终字节上限优先于逐字段上限。超限返回 `413`；core 应缩减已预览的上传摘要或分成独立案例，不能自动截断后仍显示为原完整记录。

服务端从 Key 得到 `installation_id`，不接受客户端指定归属。凭据、完整终端转录、原始模型请求/响应、SSH 主机认证信息均不在允许字段内。

### 4.3 接收响应

```json
{
  "request_id": "req-example-001",
  "record_id": "rec-example-001",
  "status": "received",
  "duplicate": false,
  "status_url": "/api/v1/records/rec-example-001"
}
```

首次持久化并入队返回 `202`。处理失败不会推翻接收结果，客户端通过状态接口查看 `failed` 和可公开的错误代码。

### 4.4 幂等、重试和修订

- `Idempotency-Key` 必填，1～128 字符，去重范围为安装标识和接口；同 Key 保留至少 7 天。
- core 重试时必须复用同一份序列化请求字节和幂等 Key；服务端按解压后 UTF-8 正文字节哈希比较，避免语义等价但字节不同的请求产生歧义。
- 同幂等 Key、相同正文：返回同一个 `record_id`，`duplicate=true`，不重新入队；状态码保持 `202`，最新处理状态另行查询。
- 同幂等 Key、不同正文：`409 IDEMPOTENCY_CONFLICT`。
- 数据库长期唯一约束为 `(installation_id, source_record_id, source_revision)`；即使幂等记录过期，也不能重复创建同一来源修订。
- 相同来源修订、相同哈希但使用新幂等 Key：复用记录；相同来源修订、不同哈希：`409 SOURCE_REVISION_CONFLICT`。
- 修订须递增，旧修订重放只能复用旧记录，不能将其覆盖为最新；来源记录删除后保留最小非正文去重标记，防止离线队列重新创建已删除记录。
- `429` 按 `Retry-After` 重试，`5xx` 和连接失败退避重试；其他 `4xx` 不自动循环。
- core 上传失败不影响原运维任务完成；队列只保存用户已同意上传的脱敏正文。

## 5. 查询记录状态

```http
GET /api/v1/records/rec-example-001
Authorization: Bearer KNOWLEDGE_KEY_REPLACE_ME
```

```json
{
  "request_id": "req-example-002",
  "record_id": "rec-example-001",
  "source_record_id": "task-demo-001",
  "source_revision": 1,
  "status": "ready_for_review",
  "updated_at": "2026-09-06T02:01:00Z",
  "published_documents": [],
  "error": null
}
```

该接口仅返回状态和关联文档标识，不返回原始正文或管理员内部批注。只允许所属安装查询；其他安装访问返回 `404`。

`processed` 表示来源已关联到审核发布完成的知识版本，不承诺该文档永久在线。记录处理状态与文档后续下架状态分别管理。

## 6. 知识检索

### 请求

```json
{
  "query": "Nginx 修改配置后怎样确认可以重载？",
  "knowledge_base_ids": ["kb-operations"],
  "filters": {
    "environment": "test",
    "software_names": ["nginx"]
  },
  "top_k": 5,
  "max_content_chars": 6000
}
```

`query` 必填，最多 2000 字符；`top_k` 为 1～10，默认 5；`max_content_chars` 为 500～12000，默认 6000。这是总正文字符预算，不是模型 Token 的精确预算，core 仍需按自己的模型上下文上限控制。

`knowledge_base_ids` 必填且不为空，最多 20 个；若请求包含任何未授权库则整体返回 `403`，不默默扩大或替换范围。过滤字段按契约枚举，不接受客户端 SQL 或任意元数据表达式。

### 响应

```json
{
  "request_id": "req-example-003",
  "retrieval_mode": "hybrid",
  "index_version": "index-v1",
  "truncated": false,
  "hits": [
    {
      "chunk_id": "chunk-example-001",
      "document_id": "doc-example-001",
      "document_version": 1,
      "knowledge_base_id": "kb-operations",
      "title": "Nginx 配置检查流程",
      "content": "重载前先执行 nginx -t。配置检查通过不代表重载已完成。",
      "rank": 1,
      "citation": {
        "label": "K1",
        "heading_path": ["检查流程", "执行前验证"],
        "line_start": 3,
        "line_end": 5,
        "source_record_ids": ["rec-example-001"],
        "document_url": "/api/v1/knowledge/documents/doc-example-001/versions/1"
      },
      "published_at": "2026-09-06T03:00:00Z"
    }
  ]
}
```

知识整理后的正文可以与原始记录不同，因此返回的是知识版本行号，同时保留来源关联；不能把编辑后的段落行号说成原始日志行号。

融合排名不等于正确概率，初版不向用户显示“可信度 98%”等无校准分数。空结果返回 `200` 和 `hits=[]`，不编造片段。

`retrieval_mode` 为 `hybrid` 或 `keyword_only`，降级时增加可读 `warnings` 数组；索引完全不可用且没有关键词通道则返回 `503`。

检索引用的来源记录 ID 只作溯源标识，不赋予读取其他安装原始记录的权限。来源详情只由管理员通过受保护页面查看。

引用详情只提供当前可访问的发布版本；旧版本已下架且调用方仍有文档库权限时返回 `410 DOCUMENT_VERSION_UNAVAILABLE`，无权限或文档不存在返回 `404`。core 展示“引用已更新/下架”，不静默替换为新版正文。

## 7. 管理接口范围

具体分页和页面字段在实现中补齐，以下业务动作与权限边界在一期固定：

| 管理路径/动作 | 目的 |
| --- | --- |
| `POST /api/admin/v1/session`、`DELETE /api/admin/v1/session` | 管理员登录、退出 |
| `/api/admin/v1/knowledge-bases` | 库列表、创建、更新、停用 |
| `/api/admin/v1/records` | 收件箱、过滤、查看脱敏来源 |
| `POST /api/admin/v1/records/{id}/retry`、`.../reject` | 人工重试、拒绝整理 |
| `POST /api/admin/v1/documents` | 手工正文或 MD/TXT 导入后建草稿，最大 2 MiB |
| `PATCH /api/admin/v1/documents/{id}/draft` | 编辑草稿、绑定多个来源、环境和标签 |
| `POST /api/admin/v1/documents/{id}/publish`、`.../unpublish` | 发起索引发布、下架 |
| `GET /api/admin/v1/jobs/{id}` | 查看索引处理状态 |
| `/api/admin/v1/knowledge-keys` | 创建、列出元数据、撤销和重新签发 |
| `DELETE /api/admin/v1/records/{id}` | 删除来源正文，保留最小去重标记 |
| `DELETE /api/admin/v1/documents/{id}` | 下架并删除正文/切片，按后台任务清理 |
| `GET /api/admin/v1/audit-events` | 操作审计 |

编辑草稿携带 `revision` 或 `If-Match`；过期写入返回 `409`，避免多个后台标签页互相覆盖。发布动作针对确定草稿修订号，不能审核 A 版本后悄悄发布 B 版本。

删除来源时如已有已发布知识关联，返回 `409 SOURCE_IN_USE`，由管理员先下架/删除关联知识，再删除来源；不能悄悄留下用户以为已删除的正文副本。删除过程中先失去检索资格，再清理物理数据。

模型管理 API 不在此业务前缀下自行复制；由受保护的 LiteLLM 控制面提供。其 `/key/generate` 等管理接口不得被公共模型路由透出。

## 8. 错误契约和初始限额

知识 API 错误格式：

```json
{
  "request_id": "req-example-error",
  "error": {
    "code": "SENSITIVE_CONTENT_DETECTED",
    "message": "检测到疑似敏感内容，请修改后上传。",
    "retryable": false,
    "fields": ["steps[0].evidence[0].excerpt"]
  }
}
```

错误响应和错误日志不回显疑似密码、Key 或完整被拒绝正文。

| HTTP | 典型代码 |
| --- | --- |
| 401 | `INVALID_API_KEY`、`EXPIRED_API_KEY` |
| 403 | `SCOPE_DENIED`、`KNOWLEDGE_BASE_DENIED` |
| 404 | `RESOURCE_NOT_FOUND` |
| 409 | `IDEMPOTENCY_CONFLICT`、`SOURCE_REVISION_CONFLICT`、`SOURCE_IN_USE` |
| 410 | `DOCUMENT_VERSION_UNAVAILABLE` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 422 | `VALIDATION_ERROR`、`UNSUPPORTED_SCHEMA_VERSION`、`SENSITIVE_CONTENT_DETECTED` |
| 429 | `RATE_LIMITED`，提供 `Retry-After` |
| 503 | `DEPENDENCY_UNAVAILABLE`，提供是否可重试 |

初始运维限额建议：每知识 Key 上传 30 次/分钟、检索 60 次/分钟，每安装待处理来源不超过 1000 条。数值为首期保护默认值，需压测后调整，不是服务容量承诺。

## 9. core 侧最小改动清单

1. 模型接入先复用现有模型设置，分别填写 endpoint、模型别名、API Key；增加必要的参数兼容回归。
2. 新增知识地址、知识 Key、目标知识库选择，Key 仍由 Rust 系统钥匙串管理。
3. 增加任务记录投影器，只导出本契约字段；上传前预览并脱敏。
4. 增加持久化、有限重试的上传队列和状态展示；重试复用序列化正文。
5. 新增知识检索服务及引用面板；在初次规划/特定失败调整前按需调用。
6. 接入 `agentContext.ts` 时使用独立 `knowledgeReferences` 字段，限制总预算并明确资料可信边界；不改变执行审批。
7. 上传与检索开关默认关闭，用户配置并启用后才向 admin 发送任务材料；禁用知识服务不影响原有模型和 SSH 工作流。

这些是后续 core 开发任务，本次文档生成没有修改 core。admin 可先通过这些契约单独实现和验证。
