# 一期方案总览：平台与知识独立

更新：2026-09-07。依据用户要求，第一期即分成独立项目，取代上一版“业务后端内知识模块”的方案。

## 项目职责

| 项目 | 负责 | 不负责 |
| --- | --- | --- |
| Opsark_admin | 管理员身份、统一 Web 后台、模型管理集成、后续用户/计费的归属 | 文档/切片/索引表与 Worker |
| Opsark_knowledge | 记录上传、知识 Key、草稿、审核发布、版本、检索、引用、处理任务 | 平台用户密码、模型渠道、付费 |
| Opsark_core | 桌面设置、模型调用、选择上传记录、展示知识引用、运维执行 | 服务端管理和知识存储 |
| LiteLLM | 上游模型适配、模型别名、模型 Key、基础用量 | 知识库、Opsark 用户系统 |

三个仓库/发布单元没有跨项目源码导入，平台数据库仅有管理员和会话。知识数据库只在 knowledge 内访问，不存在跨库外键或 join。

## 调用关系

```text
管理员浏览器 → admin:8001（登录、CSRF、管理页面）
                  └─ HTTP + 服务凭据 → knowledge:8002/internal/v1/*
core → knowledge:8002/api/v1/*（限定库的知识 Key）
core → LiteLLM:4000/v1/*（模型虚拟 Key）→ 外部模型供应商
knowledge Worker → knowledge 数据库 → 可选外部 Embedding
```

管理页面可以统一，但知识服务可以单独部署、重启和发布。生产反向代理可以将上述地址收敛为同一域名，内部仍为独立服务。

## 身份和权限

1. 平台管理员通过平台 Cookie 会话认证，修改操作验证 CSRF 和 Origin。
2. 平台调用知识服务时使用服务器环境中的服务 Token，带已认证管理员 ID 供审计；不转发浏览器 Cookie。
3. knowledge 只有验证服务 Token 后才信任管理员 ID。服务 Token 最少 32 字符，不在前端配置或 core Key 中出现。
4. core 知识 Key 由 knowledge 生成并保存哈希，具有 scope、安装标识、允许库、有效期和撤销状态。
5. 不单独建设知识用户注册系统。未来用户/空间仍由平台持有，届时设计身份委托、权限同步和租户隔离。

一期为单平台受信管理员模型，服务 Token 是高权限服务凭据，不等同完整多租户授权。内部端点不得直接暴露到公网。

## 知识处理

记录上传后在同事务持久化记录与任务，独立 Worker 生成模板草稿；管理员编辑和审核后，建立不可变文档版本，再由 Worker 切片并发布。

- 草稿不能被 core 检索。
- 新版本索引失败时保留旧发布版本。
- 下架立即清空发布指针并取消待处理任务；引用访问同时失效。
- 删除文档清理切片/版本正文；来源正文删除前检查关联文档，保留无正文的去重标记防止队列重放复活。
- Worker 采用租约、有限重试和领取时比较更新，异常详情不保存供应商秘密。

Embedding 未配置或查询调用失败时明确返回 keyword_only。首版采用小规模精确匹配/向量排序，超过 5 万切片拒绝扩大扫描；不是此前性能目标已达成的声明。

## core 设置约定

在设置中分别配置：知识 API base URL、知识 Key、目标知识库、上传开关、检索开关。上传与检索开关默认关闭，开发者可独立启用；模型 endpoint/Key 沿用原设置。

上传必须预览并脱敏，不直接上传完整 OpsTask 或开发者 JSONL。关闭上传后停止产生新任务；已有队列暂停，重新启用后由用户决定是否继续。Key 存系统钥匙串。

2026-09-07 已在 core 实现知识设置、钥匙串 Key、手动脱敏预览上传、持久上传历史、幂等重试与状态查询。检索开关当前仅保存偏好，尚未接入 Agent。使用和验收边界见 [core 知识上传说明](../../Opsark_core/docs/KNOWLEDGE_UPLOAD.md)。

## 一期边界与已知未完成项

一期仍不包含公众注册、支付、长期记忆、团队、多租户、PDF/OCR、外部抓取或本地模型推理。当前开发版已形成知识闭环和平台远程管理；正式一期验收仍需真实模型/core 联调、PostgreSQL/Docker、压力测试与备份恢复。

一条文档目前关联一条来源记录；多来源合并审核、精细权限和管理分页优化待补充，不将目标功能写成已实现。
