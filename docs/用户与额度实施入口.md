## 当前策略：直接按真实用量扣余额（2026-09-17 后续调整）

界面补漏（2026-09-17）：用户列表、详情摘要和调额表单不再固定展示预留额度；仅存在非零历史预留时显示明确标记的历史余额，流水仅在包含非零历史预留变化时展示该列。待核对调用不等于冻结额度。不清零、返还或删除真实历史账本；此次仅修正显示，网关仍使用 `begin_direct_call`，新调用 `amount=0`。

该补漏已通过前端构建、22 项账户/直接扣费测试，以及隔离数据库的浏览器冒烟测试（含零预留隐藏、非零历史余额/流水显示、刷新后恢复隐藏）。默认 Playwright 浏览器缺失，改用本机 Chrome 完成验证；未访问真实供应商或更改业务数据库。发布需更新 Admin 前端构建产物；若后端仍运行旧版本，还需重启更新后的 Admin。

按用户最新要求，新官方模型请求不再预留额度，也不使用 Token 估算量作为准入门槛。余额大于零且没有待核对/待扣调用时可发起请求；请求结束后按实际输入加输出 Token 原子扣可用余额，缓存输入目前仍计入输入总量。

同一调用只扣一次。缺少/非法 usage、或已发生用量超过余额时，保留待核对/待扣记录而非免费放行，不扣成负余额。管理员核对并补足余额后可结算。没有预留就不能保证所有并发调用都有足够余额完成结算；超时失联的调用同样需要核对。

## 核对异常预留

“用户与额度”展示调用 ID、预留数额与状态。先按调用 ID 在调用监控和供应商后台确认真实用量，不要因为失败/超时就认定免费。

当前人工核对通过管理 API 提交（使用现有管理会话及 `X-CSRF-Token`，不要把真实 Cookie 写入文档或脚本）：

```http
POST /api/admin/v1/credit-reservations/{call_id}/reconcile
Content-Type: application/json

{"actual": 50, "reason": "已按供应商记录核对输入及输出 Token"}
```

`actual` 是管理员核实后的真实计费 Token，必须是非负整数；释放差额与流水同事务完成。已结算调用的相同数额重复请求不重复扣费，改数额返回冲突。未知状态且仍在运行的调用需等待至少 20 分钟再核对。实际用量超过原预留时，只有该管理员核对入口允许在余额足够的前提下原子追加差额预留并结算，追加与结算分别留下流水；余额不足返回 402，原预留与账本不变，需补充额度后重新核对。网关不会自动追加扣减，也不会截断真实用量或释放未核实的预留。

### 官方调用预留估算与拒绝说明（2026-09-17 修复）

预留不再把整个 HTTP 请求的 UTF-8 字节数当作 Token 数。当前不携带供应商 tokenizer，采用明确标为 `exact=false` 的 `unicode_heuristic_v1_margin30_buffer1024`：普通拉丁字母每 3 字符、数字每 2 字符、常用汉字及中文标点逐字估算；长标识符、base64、罕见文字和 emoji 使用较保守的字节回退。空格按每 4 个估算，其他 ASCII 空白逐字计入。消息、工具 schema、输出格式、JSON 结构和逐消息协议开销都计入输入，在此基础上增加 30% 余量及 1,024 Token buffer，再加完整输出上限。HTTP JSON 对正文的额外转义不会重复计数；256 KiB 请求字节上限仍单独生效。

这是有安全余量的估算，不保证等于或始终高于所有模型的实际 tokenizer 结果，也不因用户余额而压低预留。余额为正仍可能不足以覆盖单次预留；需缩小上下文、降低输出上限或补充额度，而非盲目重试。最终账本始终按上游有效实际输入/输出 usage 结算。

- 原子预留不足：HTTP 402 / `INSUFFICIENT_CREDITS`，`error.details` 返回 `available_tokens`、`required_tokens`、`reserved_tokens`、`estimated_input_tokens`、`max_output_tokens`、`estimator`、`exact=false`、`retryable=false`；`error.retryable` 同样为 false。
- 未知、无效或超过预留的 usage：保留 `needs_reconciliation`，不擅自释放/追加扣费。同用户后续官方请求在派发前返回 HTTP 409 / `CREDITS_RECONCILIATION_REQUIRED`、`retryable=false`，管理员核对后才解除阻断；准入与核对状态变更使用同一账户事务锁，防止核对阻断与新准入相互穿透。
- 上述拒绝不向供应商派发、不扣费，不新增预留或额度流水；另事务保存仅含关联元数据的失败调用记录，便于 Admin 按用户/任务查到拒绝。拒绝记录没有模型 usage 或输入/输出正文，不应误认为已消费 Token。

本次无需新依赖或数据库迁移，重启 Admin 后对新请求生效；历史账本、余额与请求记录不重算、不补写。测试入口为 `tests/test_credit_estimation.py`，覆盖字符分类、结构与 schema、正余额拒绝说明、无扣费/无派发、核对阻断和人工差额核对的不足/成功/重复/并发。

额度余额不直接覆盖。调整 API 使用带正负号的 `delta`、非空 `reason` 和同一次操作保持不变的 `idempotency_key`；增加、扣减、赠额、预留与结算均写入账本。流水/预留列表最多返回 200 项；用户列表已经支持服务端搜索与分页，见下节。

## Core 模型开放范围与用户安全管理（2026-09-17 追加）

入口仍为“用户与额度”，沿用现有 Admin 风格分区展示模型范围、用户列表、额度流水和会话管理；搜索空结果、加载状态与安全操作确认已经补齐。

- **官方模型范围**：勾选“向 Core 用户开放的官方模型”后保存策略，使用现有 `RegistrationPolicy.allowed_models` 作为唯一白名单。界面显示 Core 名称、公开标识与路由/供应商状态；只有勾选且路由、供应商均启用的模型才会进入公开目录和用户可调用目录。未勾选时不展示、不能通过用户令牌调用；全不选时目录为空。不会改变独立平台模型 Key 的权限。
- Core 下次进入模型页面时刷新目录缓存，离线旧缓存只是展示；服务端对后续请求使用最新白名单。取消开放不取消已经通过鉴权的在途请求。注册开关只控制新注册，不等于官方模型开关。
- **搜索与分页**：支持邮箱/用户 ID 不区分大小写的包含查询、正常/封禁筛选；默认每页 20，界面可选 10/20/50/100。按注册时间与 ID 倒序，分页不再截断在 200 位用户。搜索和用户操作不会覆盖未保存的注册策略。
- **封禁/解封**：在“管理用户”详情中操作，必须确认并填写原因。封禁与撤销该用户全部旧会话在同一事务中完成；登录、刷新令牌和后续需要用户认证的官方接口均拒绝。解封允许重新登录，不复活旧会话、不重复赠额、不修改可用或预留额度；本地功能和 BYOK 不受影响。
- **会话管理**：展示会话 ID、有效/可刷新/已撤销/已过期状态及两类到期时间，支持筛选、分页、单个撤销、全部撤销。撤销只作用于所选用户的会话，不影响管理员登录；接口不返回访问令牌、刷新令牌、密码或其哈希。当前没有设备名称/IP/最后活跃时间采集，不将到期时间冒充登录时间。
- **安全边界**：写入必须有管理员 Cookie、CSRF、合法 Origin 和非空原因。状态变更携带 `expected_disabled`，状态不一致返回 409；取消确认不发请求。安全变更与审计同事务，重复撤销不重复记录实际变更。登录发放、刷新轮换、封禁和撤销通过同一用户行写锁串行化，避免撤销前已开始的登录绕过封禁。已通过鉴权的在途请求可能继续执行或结算。

- `/api/core/v1/client-info`：不登录、无匿名身份，按 `platform`（macos/windows/linux）、`arch`（aarch64/x86_64）和三段数字 version 查询联系信息与更新。Core 启动异步检查，也可手动检查、稍后提醒 24 小时。

## GitHub 第三方登录部署

可以使用 GitHub 登录，采用 [GitHub OAuth 授权码 + PKCE 流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)。客户端在系统浏览器授权，返回后点击“已授权，完成登录 / 绑定”；仅请求 `read:user user:email`，不请求仓库权限。

在 GitHub 创建 OAuth App，通过部署 Secret 注入以下配置（Compose 已透传，源码无生产凭据）：

| 配置 | 用途 |
| --- | --- |
| `GITHUB_CLIENT_ID` | GitHub OAuth App Client ID |
| `GITHUB_CLIENT_SECRET` | 仅服务端保存，禁止写入 Core、日志或前端构建变量 |
| `GITHUB_CALLBACK_URL` | 固定 `https://平台域名/api/core/v1/auth/github/callback`，必须与 GitHub OAuth App 设置一致 |
| `MODEL_KEY_ENCRYPTION_KEY` | 现有 Fernet 密钥，同时保护私有 Skill、工单与短期 PKCE verifier；丢失会导致内容不可读，必须安全备份并规划轮换 |
| `RELEASE_ALLOWED_HOSTS` | 下载主机名白名单，逗号分隔；不包含 scheme/path |

上述 OAuth 配置不完整时 Core 显示未启用，不影响密码登录和本地功能。回调必须是生产可访问 HTTPS 地址；本地用 mock 验证，不绕过回调安全限制。

服务端校验随机 state、GitHub PKCE 和桌面独立证明，10 分钟过期，回调和完成操作不可重放。按 GitHub 稳定用户 ID 绑定，必须有已验证主邮箱。同邮箱已有 OpsArk 账号不自动合并：先用密码登录，再显式绑定。新 GitHub 用户遵守相同注册开关和一次赠额策略；绑定不会重复赠额。GitHub Access Token 不持久化、不下发桌面；桌面仅保存 OpsArk 会话。

默认 Uvicorn 访问日志会去除该回调的查询参数；反向代理、CDN、APM 也必须配置为不记录 code/state/Authorization/Cookie，不能假设应用过滤能覆盖上游访问日志。真实 OAuth App、回调与桌面钥匙串仍需部署后验收。

## 保留期与运行维护

为运行 Admin 的相同环境安排每小时 `python -m app.maintenance`（Compose 可由宿主机定时执行 `docker compose exec -T api python -m app.maintenance`）。它清除到期工单密文和过期 OAuth verifier；读取反馈时也触发过期清理。**开发期间没有对真实库执行维护命令。**

用户删除与保留期清理只作用于在线库正文，保留工单/变更/审计元数据；备份副本必须另设保留期与访问控制。不要把备份长期留存误认为已经完成全面删除。Skill 删除保留版本墓碑，避免旧设备静默复活内容。限制、审计和加密不是公开注册防刷替代品；共享限流、邮箱验证/找回等发布门禁仍需完成。

追加验证：全量 Python 77 项通过（含旧库/空库迁移、云资源隔离、冲突、工单保留期、OAuth 重放与一次赠额）；新云模块 Ruff 通过，Admin 前端构建通过。增强后的独立 Chrome 脚本还验证了公开模型名称、联系策略保存、发布版本引导、反馈查看/回复与用户查询；没有真实 OAuth 或收费上游调用。

## 系统 Skill、工具配置与版本管理（阶段 D1）

- 管理入口：**系统 Skill** 编辑官方工作流，**工具管理** 调整内置工具启停、名称说明和参数协议，**版本管理** 发布系统版本与官网下载地址。前两者都有草稿、发布说明、最低 Core 版本、不可变发布历史、撤回及历史内容复制；保存草稿不会影响客户端。
- 初始目录包含 7 个系统 Skill、13 个内置工具，位于 `app/resources/core_catalog.json`。在 Core 目录执行 `node scripts/export-official-catalog.mjs` 可重新生成；工具实现变化后随 Admin 一起部署新目录。新增工具不通过远程执行代码分发。
- `GET/PUT /api/admin/v1/official-content/{skills|tools}` 读取/保存草稿，写入携带当前 `revision`；冲突返回 409，不覆盖别人的修改。
- `GET/POST /api/admin/v1/official-content/{kind}/releases` 查询/发布；`GET/DELETE .../releases/{id}` 查看内容/撤回。发布携带最新草稿 revision、递增发布 version、最低 Core 版本及说明；系统 Skill 单项内容变化时自动递增自身版本。工具内容包含 ID、启用状态、目录实现版本、名称说明和 `inputSchema`。参数名称、类型、内置执行协议与硬限制保持兼容，可调整默认值、增加必填项、收紧枚举/取值范围/长度/数量限制；执行代码随 Core 升级。
- 公共 `client-info` 增加 `system_skills` 与 `tools` 发布元数据，按当前 Core 版本与 `content_protocol` 返回最新兼容发布（新版传 2，旧版默认 1；工具参数包采用 schema 2，Skill 仍为 1）；固定源站的 `/api/core/v1/official-content/{kind}/{id}` 返回正文和 SHA-256。未发布或无兼容版本返回 null，不创建账号。
- 撤回停止新下载，不会远程删除已经激活的本地版本；恢复旧内容需要复制历史到草稿并发布更高版本。离线客户端使用最后一次有效缓存。
- 部署：备份数据库后执行 `python -m alembic upgrade head`，构建 `web` 并重启 Admin；Core 新增 Rust IPC，桌面开发进程需重新编译/启动才能使用。生产域名、真实下载地址和安装包校验值仍由运营填写。
- 验证：在 Admin 根目录运行 `.venv/bin/pytest -q tests/test_official_content.py tests/test_migration.py`；构建两端后运行 `OPSARK_SMOKE_BROWSER=chrome node scripts/smoke-official-content.mjs`。测试使用临时数据库和隔离浏览器，不发布到实际服务。


工具参数更新：展开“编辑工具配置”修改参数 JSON，保存草稿再发布；“恢复内置参数”只更改当前草稿，发布后才生效。Core 会在参数省略时填入发布的默认值，并在规划及执行前校验最新约束。修改已存在的参数配置无需安装新工具实现；新参数和新能力需升级 Core。原有发布历史保留，可复制后发布更高版本。本次沿用 JSON 草稿/发布表，无额外数据库迁移。
