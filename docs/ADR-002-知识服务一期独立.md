# ADR-002：知识服务在第一期独立

日期：2026-09-07。状态：已采纳并实施基础拆分。

## 原因

用户明确要求知识库单独创建平级项目；平台后续会承载模型接入、用户和计费等，不应持有知识内部数据结构。

## 决策

- `Opsark_admin`：平台身份、统一管理界面、模型控制面集成。
- `Opsark_knowledge`：知识数据、上传、审核、检索、Worker 和知识客户端 Key。
- 两个服务各有依赖、迁移、运行配置和数据库；不存在跨项目 Python 导入、共享 ORM 或跨库 join。
- 前端管理操作由 admin 白名单 HTTP 适配到 knowledge 的 `/internal/v1`。
- core 直接调用 knowledge 的 `/api/v1`，平台服务凭据永不交给 core。
- 单个高权限服务 Token 适用于当前单平台管理员版本；未来多用户时另行设计身份委托和细粒度权限，不假装当前已实现多租户。

## 迁移结果

之前未完成骨架中的知识 ORM、请求 schema 和知识数据库模块已从 admin 移至 knowledge；admin 重建为仅管理员/会话模型。没有迁移、删除或覆盖用户数据库。

当前使用新的 `platform.db`、`knowledge.db` 文件名。如果已有旧 `opsark.db`，不要直接套新 schema；保留备份，后续设计一次性数据导入。

## 运行边界

内部 API 仅在可信网络开放，并检查 Bearer 服务凭据。远程部署使用 TLS；客户端伪造 `X-Opsark-Actor` 而没有服务 Token 无效。平台使用固定上游 URL、禁止重定向和路径白名单，知识故障返回 503。

平台和知识启动、发布、数据库升级、备份分别进行。共享 Compose 外部网络只是开发连接方式，不构成共享数据库依赖。

## 已知成本

需要两套配置、服务凭据轮换、网络故障处理和集成验证。当前没有实现分布式事务；记录、任务、文档发布等一致性操作全部留在 knowledge 内部事务中。
